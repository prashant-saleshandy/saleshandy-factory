Design v1 For review 2026-10-20

Saleshandy Factory

The factory is a Claude Code plugin. It moves a big feature or fix from a Jira ticket to merged PRs and a prod release doc. It keeps the code quality high and the token cost low.

The factory starts only when a developer types /factory <prompt>, for example /factory SH-123456, continue phase 2. A normal session never starts it by mistake. Hooks (scripts that Claude Code operates at fixed events) enforce the hard rules. Thus the rules do not depend on the memory of the agent.

This page is the design only. Nothing is built yet. Annotate a section to change it. When you approve the page, the build starts.

Design principles

One command

/factory is the only command. After it, you talk in normal words, and the agent asks you questions with options when it needs a decision.

Rules in code, not in prompts

Hooks and scripts do the spec gate, the git rules, the subagent limit and the context limit. A script costs no tokens and does the same steps each time.

One source of truth at a time

Before approval, the spec is a local HTML draft. After approval, the Confluence tech analysis page is the only source of truth.

Token budget in each stage

Each stage reads only its handoff files. Subagents return conclusions, not file dumps. Each step can start a maximum of three subagents.

The pipeline

The pipeline has six stages. The first two stages operate one time for each work. The last four stages operate one time for each phase. A work without phases has one phase. A gold border shows a stage where the factory stops for a human.

Two layers

The factory has a shared core and a personal layer. The core is the same for all developers and QAs. The personal layer holds the choices of one person. At this time, the personal layer holds only your choices.

LayerLocationContents
Core (part 1)github.com/prashant-saleshandy/saleshandy-factory, public. Local clone at saleshandy/factory.Stage skills, subagent definitions, hooks, scripts, templates. No internal hosts, tokens or repo architecture.
Personal (part 2)~/.claude/factory/config.json with two limits. Stage notes in plain words. Temporary repo profiles, for example profiles/edge.md.
Repo knowledge (later)Each org repoOut of scope at this time. Later, the repo profiles move upstream into each repo.

The plugin installs at user scope in ~/.claude/settings.json. Thus no org repo changes. The factory reads the lint, typecheck, build and test commands from the package.json of each repo when it operates.

config.json holds only the two limits that hooks read. Hooks need exact numbers, so these two values stay in a file.

// ~/.claude/factory/config.json
{
  "maxSubagents": 3,
  "contextLimitTokens": 100000
}

All other personalization is stage notes: short files in plain words, one file for each stage, for example ~/.claude/factory/notes/tester.md. A stage reads its notes file when it starts. The files are optional, and the factory works the same without them.

You do not write these files by hand. If you correct a stage in the same way two times, the agent asks you one question: "Keep this as a rule for the tester?" If you agree, the agent adds one line to the notes file. Thus the factory learns how you work from your corrections, and each note is short and real.

# ~/.claude/factory/notes/tester.md (example, written by the agent)
- Test edge APIs against staging, not a local server.
- Ask before UI automation.

The work folder

The factory indexes work by ticket ID, not by repo. Each work has one folder under saleshandy/worktrees/. The folder holds one git worktree for each repo and a .factory/ folder for the state. The worktrees folder is not a git repo. Thus nothing in .factory/ can be committed by mistake.

saleshandy/worktrees/SH-123456/
  edge/                 git worktree on feat/SH-123456
  webui/                git worktree on feat/SH-123456
  background-jobs/      git worktree on feat/SH-123456
  .factory/
    state.json          stage, phase, approved spec version, PR links
    context.md          handoff from stage 1 (size limit)
    facts.md            code facts with file:line citations
    spec.html           lavish draft (kept or deleted, your choice)
    spec.cache.md       read-only copy of the Confluence page and its version
    test-plan.html      lavish test plan with checkboxes
    release-notes.md    release steps that a diff cannot show
    secrets.json        share password and update_key (never committed)
    .env                tester credentials (never committed)

The stages

1. Context builder

This stage turns the unstructured input into a short, scoped starting point for the spec. You give a ticket ID, an epic link, pasted Basecamp text, PRDs or other references. The agent reads Jira and Confluence through the Atlassian MCP.

The agent then finds the state of the work. It looks for an epic, for feat/SH-* or fix/SH-* branches in each repo, and for a work folder.

  • If the work is ongoing, the agent uses the epic, branches and folder that exist.
  • If the work is new, the agent tells you what it will make: the epic, the branches and the worktrees. It makes them after you agree.
  • If the signals do not agree, the agent asks you to choose the epic, the branch names, or a new epic.

Output: context.md, with a size limit. Later sessions read this file and do not read the sources again. If the requirements change, you ask the agent to update the file. The factory does not detect such changes itself.

2. Spec writer stops for you

This stage makes the tech analysis, the source of truth for all development. It is a loop: research, a proposal, your questions, your fixes, and then approval.

Research goes deep, and the agent decides what to read from the scope of the work. It does not stop at one or two layers. It follows each related flow until it knows the real constraints, for example in code, data, workflows or scale. A maximum of three read-only subagents help with this research. They write only facts with citations into facts.md. The builder and the reviewer use the same facts and do not search again.

The agent writes the draft in spec.html with the lavish skill, and you annotate it in the browser. The agent asks a question only when the code cannot answer it, in the style of grill-with-docs. Each requirement gets an ID, for example R1, with acceptance criteria. For big work, the spec divides the requirements into phases.

Approval happens in this sequence:

  1. The agent asks you a question with two options: "Approve the spec" and "Discuss changes".
  2. A hook reads your selected option from the tool result and records the approval. The agent cannot write this record itself, and a normal message never counts as approval.
  3. The agent lists the Confluence spaces and asks you which space to use.
  4. The agent makes the parent page and the tech analysis page. It records the page version as the approved version.
  5. The agent makes the Jira phases and tasks under the epic.
  6. The agent asks you if it can delete spec.html. If you keep it, it adds a line at the top: "Superseded by Confluence vN".

After approval, all spec changes go to Confluence first. A new page version closes the gate, and the builder cannot edit code until you approve again. Agents read spec.cache.md, which the agent refreshes through the MCP after each spec change. A hook blocks direct edits to the cache.

3. Builder

The builder is an orchestrator. It divides the phase into tasks, gives each task to a subagent, and supervises the subagents. It starts the minimum number of subagents, with a maximum of three. Each subagent gets a repo, a list of requirement IDs and the related facts.

Each decision obeys these criteria: alignment with the spec, security, maintainability, UI and UX, and Saleshandy conventions for the stack. If the code cannot do what the spec says, the builder stops and tells you. You update the spec first, and then the builder changes the code.

If the phase changes a TypeORM entity, the builder prints the incremental staging SQL in the terminal. You send it to the responsible person, or you operate it yourself.

4. Reviewer stops for you

The reviewer starts in a new context with only the spec cache, the facts and the diff. Thus it does not share the assumptions of the builder. It reports three lists by requirement ID: requirements with no code, code with no requirement, and problems from the security, UX, UI and code lenses.

The reviewer fixes nothing. It tells you about each drift. You decide if the builder fixes the code or if the spec changes. The stage ends when the code and the spec agree.

5. Tester

The tester plans the tests itself from the spec, the requirement IDs and the code. It writes the plan to test-plan.html, with one section for each phase and one checkbox for each item. It marks each item when the item passes. Your tester notes, if they exist, change how it plans.

The tester asks you for the credentials that it needs and writes them to .factory/.env. It reads data through pyxis-grafana for staging or grafana for prod, and it chooses the source itself.

A failed item goes to the builder and then to the reviewer. Then the tester does the failed items again. At the end, it operates lint, typecheck and build in each repo.

6. Approver stops for you

The approver does no review and no tests. It accepts its input as fully tested. A script does the git flow, the PR titles, the PR bodies and the shares. The agent writes only the summary points.

  1. Show you the branches, PRs and Jira changes. Ask a question with the options "Push and open PRs" and "Discuss changes".
  2. Push feat/SH-123456 and open or update the draft PR to main in each repo.
  3. Make the phase staging branch, merge the work branch into it, and open the PR to staging.
  4. Share test-plan.html through lavish-axi share --password. Keep the password and update_key in secrets.json.
  5. Update the Jira tasks of the phase.
  6. Make the release doc again and show it to you. Ask a question with the options "Approve the release doc" and "Discuss changes". After approval, update the Confluence page.

Release doc

The release doc is for prod only. It lists only the PRs to main, the prod SQL and the prod steps, in order. It contains no staging references. It links to the test plan share.

The approver makes the full doc again in each phase from the final state of each feat/SH-123456 branch compared with main. It does not append to the old doc. Thus the staging history, for example a create and a later alter, never reaches prod. The prod SQL is one combined statement for each table, made from the full TypeORM entity diff.

Some steps do not show in a diff, for example a data backfill or a manual check. Only for these steps, the agent keeps release-notes.md during the work. Phase 1 makes the Confluence page, and each later phase updates the same page.

Release: SH-123456 - pre warmed mailboxes / domain
Test plan: <share link> (password from the owner)

1. Operate this SQL on prod:
   CREATE TABLE ... (final columns only)
2. Merge edge PR #1234 to main and deploy.
3. Merge background-jobs PR #567 to main and deploy.
4. Make sure that the new queue is consuming jobs in Grafana.
5. Merge webui PR #890 to main and deploy.

Git flow

Each repo in the work uses the same branch names. The PR to main is one draft PR for the full work. The PRs to staging are one for each phase.

ItemTo mainTo staging
Branch, no phasesfeat/SH-123456feat/staging/SH-123456
Branch, phasedfeat/SH-123456feat/staging/SH-123456/p1
PR title, no phasesfeat(SH-123456) - title[STAGING] feat(SH-123456) - title
PR title, phasedfeat(SH-123456) - title[STAGING] feat(SH-123456/P01) - title
PR stateDraftOpen
PR bodycontext (spec link), summary, tests (test plan link)context (spec link, main PR link), summary, tests
 
git checkout staging
git pull origin staging
git checkout -b feat/staging/SH-123456/p1
git merge --ff feat/SH-123456

Git cannot keep feat/staging/SH-123456 and feat/staging/SH-123456/p1 together. Thus a work stays in one mode. If a work without phases becomes phased, the approver asks you before it removes the old staging branch.

If a merge has a conflict, the factory stops and tells you. It never resolves a conflict unless you tell it to.

Confluence and Jira

Confluence (space chosen at approval)
  SH-123456 - title           parent page
    Tech analysis             made by stage 2
    Release doc               made by stage 6
Jira
  Epic SH-123456
    [PHASE - 01] - title      task
      work item               subtask
      work item               subtask
    [PHASE - 02] - title      task

Jira allows only epic, task and subtask levels. Thus each phase is a task, and each work item is a subtask. A work without phases puts its tasks directly under the epic. All PRs and the epic link to the Confluence parent page.

Hooks

EventJob
SessionStartIf the current directory is in a work folder, add about five lines of state to the session.
PostToolUse on AskUserQuestionRecord an approval only when you select an approval option. This covers the spec, the push and the release doc.
PreToolUse on Edit and WriteBlock code edits in the worktrees unless the current spec version has an approval. Block edits to spec.cache.md.
PreToolUse on BashBlock git rebase, force push and direct commits on staging branches. Stop on a merge conflict.
PreToolUse on AgentBlock a fourth subagent in one step. The limit comes from config.json.
StopRead the token count of the last reply from the transcript. Above the limit, tell the agent to write the handoff.

Sessions and tokens

Each stage starts in a new session, because each stage reads only its handoff files. The short loops, for example tester to builder to reviewer, stay in one session. A restart on each loop costs more tokens than it saves.

The default context limit is 100,000 tokens, and you can change it in config.json. Above the limit, the agent finishes its current task, updates the state and tells you to start a new session. An agent cannot open a session itself. Thus you type /clear or open a new terminal, and the SessionStart hook loads the state.

  • Scripts do the deterministic work: branches, PR text, worktrees, shares.
  • Handoff files have size limits, and requirement IDs replace long descriptions.
  • Skills keep a short main file and load reference files only when necessary.
  • Subagents return conclusions and citations, not file contents.
  • The tester does only the failed items again, not the full plan.

Phased mode

For big work, the spec divides the requirements into phases. Each phase goes through builder, reviewer, tester and approver before the next phase starts. Each phase gets its own staging branch and staging PR, so you can test it on staging. Prod gets one release at the end, from the one release doc.

Plugin structure

  .claude-plugin/        plugin.json, marketplace.json
  skills/
    factory/             /factory entry: start or continue a work (user only)
    context/  spec/  build/  review/  test/  ship/
    lenses/              security, ux, ui, code checklists
  agents/                researcher, implementer, reviewer definitions
  hooks/hooks.json
  scripts/               worktree, state, gate, git flow, share, context size
  templates/             spec.html, test-plan.html, PR bodies, release doc

The aihero skills for research, grill-with-docs and implement-spec are inputs to the stage skills. The build adapts them, and it does not copy them as they are.

Build order

  1. Make the repo, the plugin skeleton, the state file, the worktree script and the hooks.
  2. Build the context builder and the spec writer, with the Confluence and Jira steps.
  3. Build the builder and the reviewer.
  4. Build the tester and the stage notes.
  5. Build the approver script, the shares and the release doc.
  6. Do a pilot on your ongoing work, and then correct the design.

Risks

If an agent writes files through Bash and not through Edit, the spec gate can miss the change. The Bash hook blocks the common write patterns. You accepted this limit.
If the PreToolUse event for subagents does not give enough data to count them, the limit falls back to an instruction in the skill. The build will find this out in step 1.
If a share password leaks, anyone with the link can read the test plan on ht-ml.app. This risk stays until the in-house host is ready.
